## 9. Trade-offs

| Decision | Benefit | Cost / accepted risk |
|---|---|---|
| Node-RED bridge | Fast visual adaptation and experimentation | Additional runtime and distributed logic ownership. |
| SQLite outbox | Durable local capture across outages | Locking, retention, concurrency and replay-state complexity. |
| At-least-once + dedupe | Avoids distributed transactions | Duplicate/conflicting payload policy becomes explicit work. |
| PostgreSQL relational storage | Constraints and contextual joins | Telemetry scale/retention not measured; possible future partition/TSDB need. |
| JPA plus native queries | Productive CRUD plus targeted SQL | Two query models and mapping/schema drift risk. |
| Flyway plus `ddl-auto=update` | Lab convenience | Competing schema authorities and reduced reproducibility. |
| Basic correlation/logs/health | Useful diagnosis | Not full tracing, metrics, SLOs or observability platform maturity. |
| Permissive local security | Faster experiments | Unacceptable outside a controlled lab. |

## 20. Revised DEFENSE GAPS

### G1 — Outbox, retry and concurrent replay

- **TOPIC:** at-least-once, state machine, backoff, dead-letter and SQLite concurrency.
- **WHY:** this is the strongest reliability story and the easiest to overstate.
- **PROJECT EVIDENCE:** outbox worker/schema and PR #5.[^G7]
- **MUST EXPLAIN:** PENDING/SENDING/SENT/FAILED/DEAD_LETTER; backend-processed/no-ack case; replay while new telemetry arrives.
- **TRADE-OFF QUESTION:** SQLite outbox versus a persistent broker or alternative embedded store.
- **INTERVIEW QUESTION:** “What happens when new telemetry arrives while an offline backlog is replaying?”
- **EXPECTED ANSWER ELEMENTS:** ordering/fairness, locking, batching, idempotency and unvalidated paths.
- **15–30 MIN PRACTICE:** model six failures and one concurrent-ingest scenario, predicting both edge and platform states.

### G2 — Technical versus semantic dedupe

- **TOPIC:** idempotency keys, conflicting payloads and invariants.
- **WHY:** key-based dedupe does not prove two messages are semantically identical.
- **PROJECT EVIDENCE:** unique constraints and PR #7.[^G8]
- **MUST EXPLAIN:** identical resend, same ID/different payload and current first-value policy.
- **TRADE-OFF QUESTION:** ignore, reject, update, version or audit a conflict.
- **INTERVIEW QUESTION:** “How do you detect that the same message ID carries a different event?”
- **EXPECTED ANSWER ELEMENTS:** explicit policy, hash/canonicalization options, audit trail and current limit.
- **15–30 MIN PRACTICE:** create a four-case ID/payload decision table.

### G3 — Lab security boundary

- **TOPIC:** API identity/authorization, MQTT TLS/ACLs, device identity and secrets.
- **WHY:** the current controlled lab intentionally lacks Production controls.
- **PROJECT EVIDENCE:** permissive Spring security, Mosquitto and Compose configuration.
- **MUST EXPLAIN:** why acceptable locally, threat outside the lab and hardening order.
- **TRADE-OFF QUESTION:** experimental speed versus security from inception.
- **INTERVIEW QUESTION:** “What must change before connecting a real farm device?”
- **EXPECTED ANSWER ELEMENTS:** TLS/mTLS, per-device identity, topic ACLs, secret management, RBAC and network isolation.
- **15–30 MIN PRACTICE:** produce a five-asset threat model and prioritized controls.

### G4 — Temporal data and scale

- **TOPIC:** event/receive/process time, late data, windows, indexes and retention.
- **WHY:** semantics exist; real volume behavior does not.
- **PROJECT EVIDENCE:** PRs #6 and #12.[^G9][^G13]
- **MUST EXPLAIN:** required event time, late arrival, ordering, current windows and pagination.
- **TRADE-OFF QUESTION:** PostgreSQL versus partitioning/TimescaleDB/TSDB.
- **INTERVIEW QUESTION:** “What would fail first at ten million readings per day?”
- **EXPECTED ANSWER ELEMENTS:** no invented capacity; benchmark, indexes, partitioning and retention.
- **15–30 MIN PRACTICE:** define a small benchmark with dataset volume, queries and percentiles.

### G5 — Schema authority

- **TOPIC:** Flyway versus Hibernate `ddl-auto=update`.
- **WHY:** both currently influence schema evolution.
- **PROJECT EVIDENCE:** backend configuration/migrations.[^G11]
- **MUST EXPLAIN:** drift risk and the desired single source of truth.
- **TRADE-OFF QUESTION:** lab convenience versus reproducible migration control.
- **INTERVIEW QUESTION:** “Which mechanism owns the database schema?”
- **EXPECTED ANSWER ELEMENTS:** current duality, Production preference and migration verification.
- **15–30 MIN PRACTICE:** narrate one incompatible schema change and its safe migration.

### G6 — From engineering lab to AI/Big Data research result

- **TOPIC:** falsifiable question, dataset, baseline, protocol, metrics and threats to validity.
- **WHY:** AI/Big Data is central to the intended future project but absent now.
- **PROJECT EVIDENCE:** exercise branches/runbooks and current lack of AI artifacts.
- **MUST EXPLAIN:** future problem, hypothesis, dataset provenance, comparison and evaluation.
- **TRADE-OFF QUESTION:** resilience-focused systems research versus model-focused AI research.
- **INTERVIEW QUESTION:** “What AI hypothesis will Glea-Nexo test, and what result would falsify it?”
- **EXPECTED ANSWER ELEMENTS:** bounded agricultural objective, non-AI baseline, reproducible evaluation and limits.
- **15–30 MIN PRACTICE:** draft one hypothesis with input data, target, baseline, metric and falsification condition.

### G7 — Human ownership with agent assistance

- **TOPIC:** ownership of decisions versus generated implementation.
- **WHY:** architectural ownership is settled; implementation attribution is not fully itemized.
- **PROJECT EVIDENCE:** `agents.md`, commits/PRs and physical validation evidence.
